# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Qlone is an early-stage first-person puzzle game built in **Unity 6 (6000.0.72f1)** with the **Universal Render Pipeline (URP)**. The central mechanic: the player spawns a stationary *clone* of themselves and switches control back and forth between the two bodies (split-screen), using both to solve environment puzzles (doors, keycards, pickable objects, levers, lifts). When a clone is dismissed it collapses into a physics **ragdoll** corpse that stays in the world and can be picked up.

All first-party code lives in `Assets/_App/`. Everything under `Library/`, `Packages/`, and the various `com.unity.*` caches is Unity/third-party and should not be edited. The C# is thirty small files in `Assets/_App/Scripts/`: a `Character/` folder (player/clone behaviour), a `Door/` folder with a `Conditions/` subfolder (the puzzle-door system), a `Modular/` folder (corridor-kit data), an `Editor/` folder with a `Modular/` subfolder (authoring tools), and `TextController`, `SecurityMonitor`, `MovingPlatform` and the `IInteractable` interface at the root.

There are **no asmdefs**, but the code still splits across **two assemblies**, because Unity treats any folder named `Editor/` specially: the 5 files under `Scripts/Editor/` compile into **`Assembly-CSharp-Editor`** and everything else into **`Assembly-CSharp`**. The dependency is one-way — editor code may reference runtime code, never the reverse — and `Editor/` code is stripped from player builds. **Consequence:** a `MonoBehaviour` that lives on a prefab or scene object must NOT go under `Editor/`, even when only a tool writes to it. That is why `CorridorPiece.cs` sits in `Scripts/Modular/` while the tool that fills it in sits in `Scripts/Editor/Modular/`.

## Working in this repo

This is an **Editor-driven project** — there is no CLI build pipeline and no scenes are registered in `EditorBuildSettings` (`m_Scenes: []`; build via Unity's *Build Profiles* window). Develop and run by opening the project in Unity 6000.0.72f1 and entering Play mode in `Assets/_App/Scenes/DemoLevel.unity` (the main scene; `TestScene.unity` is a scratch scene).

**Offline compile check.** The Unity-generated csprojs do build with the `dotnet` SDK, which is the only way to typecheck without a running, focused Editor:
```bash
dotnet build Assembly-CSharp.csproj -v q --nologo         # runtime code (~30s)
dotnet build Assembly-CSharp-Editor.csproj -v q --nologo  # editor tools
```
It reports real `error CS…` lines with file:line, and ~37 pre-existing warnings from URP/package code that are **not** yours — grep for `error CS` and the `N Error(s)` summary. **Two caveats:** the csproj `<Compile Include>` list is a *static snapshot* Unity regenerates, so a **brand-new `.cs` file is silently invisible** to this build (it will report `0 Error(s)` however broken the new file is) until `refresh_unity` (`scope: all`) has imported it — the same new-file trap as below; and it typechecks only, so it can't tell you a component wired up correctly. For anything involving the live Editor, still prefer `refresh_unity` + `read_console`.

The **Unity MCP server** (`com.coplaydev.unity-mcp`) is installed and connected, so you can drive the live Editor directly instead of asking the user to. Practical loop:
- After editing scripts, call `refresh_unity` (with `wait_for_ready`), then `read_console` (filter to `error`) to confirm a clean compile **before** assuming a type/component is usable. The readiness/compile state lives in the `editor_state` resource (`mcpforunity://editor/state`) under `compilation.is_compiling` and `advice.ready_for_tools`.
- **Gotcha:** creating a *brand-new* `.cs` file needs a full asset refresh (`refresh_unity` with `scope: all`) so Unity imports it — `scope: scripts` recompiles existing files but won't pick up the new asset, and references to the new type will fail to compile.
- **`advice.ready_for_tools` stays `false` longer than the compile does.** It routinely reads `false` with `blocking_reasons: ["stale_status"]` (the Editor is unfocused, so its status heartbeat is stale) *after* compilation has actually finished. Don't poll it in a loop — read `compilation.is_compiling` and whether `last_domain_reload_after_unix_ms` has advanced, then just issue the call.
- **`read_console` truncates a multi-line `Debug.Log` to its first line.** A 40-line diagnostic dump comes back as its heading and nothing else, which silently looks like the code did nothing. For anything longer than one line, have the throwaway script `File.WriteAllText` to the scratchpad and `cat` it instead.
- **To write private serialized fields onto a prefab asset, edit prefab *contents*** rather than fighting `manage_prefabs modify_contents`: `PrefabUtility.LoadPrefabContents(path)` → mutate the returned root → `PrefabUtility.SaveAsPrefabAsset(contents, path)` → `PrefabUtility.UnloadPrefabContents(contents)` in a `finally`. This is how the corridor sockets get baked, and it reliably reaches `[SerializeField]` privates that MCP reports "no changes" for. Scene instances then pick the values up through prefab inheritance.
- Input simulation isn't available over MCP — you can enter Play mode and read the console, but you can't press keys or screenshot the Game view. Treat gameplay changes as *verified-compiles*, not *verified-in-play*; ask the user to confirm feel/visuals.
- `manage_editor` controls Play mode; `manage_prefabs` edits prefab assets headlessly (`modify_contents` with `target` = the GameObject the change/child applies to). Paths passed to MCP tools are relative to `Assets/` with forward slashes.
- Prefer reading live state over the on-disk YAML: the `mcpforunity://project/layers` resource, camera culling masks, etc. can be ahead of `ProjectSettings/*.asset` until the user does *File → Save Project*. `manage_prefabs modify_contents` sometimes reports "no changes" on private serialized fields — verify with a read, and fall back to editing the prefab YAML directly for a stubborn value.
- **`manage_gameobject action:modify` silently ignores `is_static: false`** (it reports "No modifications applied", and the string `"false"` coerces to *true*). There is no MCP route to clear a Static flag, which any object you intend to move at runtime needs. Workaround: write a throwaway editor script with a `[MenuItem]` calling `GameObjectUtility.SetStaticEditorFlags(go, 0)`, `refresh_unity` (`scope: all`), `execute_menu_item` on that path, then delete the script. UnityEvent wiring is also **not** readable through the component resource (it returns `{}`) — grep the prefab/scene YAML for `m_MethodName` to confirm a binding.

There are **no unit tests** in the project, though the Unity Test Framework package is present. If you add tests, create an asmdef + test assembly and run them via `run_tests` (MCP) or the Editor's Test Runner.

## Architecture

The scripts are small but coupled through Unity Editor wiring, prefab inheritance, and runtime tag/layer lookups rather than through code references. The following conventions are **load-bearing** and not visible from reading any single `.cs` file.

### Character prefabs: one base, one variant
- `Prefabs/Character/MainCharecter.prefab` is the player (root tagged `Main`, layer `Player`). It carries `FPS_Controller`, `Cloning`, `GrabScript`, `GrabIK`, `ViewmodelArms`, `InputManager`, `CharacterAnimator`, a `CharacterController`, a kinematic `Rigidbody`, and a child `Camera`.
- The runtime clone spawns from **`CloneNested.prefab`, a prefab *variant* of MainCharecter** (referenced by `Cloning.CloneGO`). The variant renames the root, tags it `Clone`, puts the model on the `CloneBody` layer / arms on `CloneArms`, disables `FPS_Controller`, removes `Cloning`, and overrides the camera's culling mask. **`Clone.prefab` is an older, unused version — editing it has no runtime effect.**
- **Consequence:** components/objects shared by both bodies should be added to **MainCharecter** (the base) — they propagate to the player, the scene instance, *and* the clone variant. This is how `CharacterAnimator`, `GrabIK`, `ViewmodelArms`, and the `Camera/HoldPoint` anchor reach both bodies from a single edit.
- The visible body is the **`FirstCharacter`** humanoid model (a nested FBX with an `Animator`, controller `MainCharacterController` assigned, root motion off). The `Camera` carries the first-person arms under **`Camera/Arms`** — a static `CameraViewArms` mesh plus a rigged `metarig` skeleton driven by `GrabIK`/`ViewmodelArms` — and a `HoldPoint` empty (the grab/hold anchor).

### Input is wired in the scene, not in code
`Character/InputManager.cs` is the only input entry point: it exposes `KeyCode` fields plus `UnityEvent`s (`OnQDown/Up/Hold`, same for `F`, `E`, `R`, and `Interact`) and invokes them each frame. **Which method a key calls is configured in the Inspector**, and every binding targets the **player's** component instances (so they run even while the clone is in control, acting on the active body via `Camera.main`). Current wiring on the MainCharecter `InputManager`:
- **Q** → `Cloning.Clone`
- **F** → `Cloning.SwitchClone`
- **E** → `GrabScript.ReleaseObject` then `GrabScript.PickUpObject` (drop + grab/swap)
- **R** → `GrabScript.ReleaseObject` then `Cloning.DestroyClone` (drop + ragdoll the clone)
- **Interact** (`G` in code, but wired to **E**) → `Interactor.Interact` (press a looked-at button/switch/lever)

Note that Interact and the grab pair are both bound to **E**, so one press runs *both*: pressing E at an interactable also drops whatever the active body is carrying. Interactables are on the `Default` layer without a Rigidbody, so they're never grabbed by the same press.

To change a binding, edit the event wiring in the prefab/scene — grepping code won't reveal it.

### Cloning and control-switching (`Character/Cloning.cs`)
Lives on the player root. Key behaviours:
- `Clone()` raycasts around the player for a clear spot, instantiates the clone, and **animates the split-screen open** (coroutine `LerpRect` eases each `Camera.rect`; the player view shrinks left while the clone view slides in from the right). Split-screen uses oversized viewport rects (`width/height = 5`); the rest/target rects are serialized fields.
- **Exactly one camera is tagged `MainCamera` at a time** — a load-bearing invariant. `Camera.main` and every "is my view active?" check (ViewmodelArms look-sway's `CompareTag("MainCamera")`, GrabScript raycasts) depend on it. The clone's camera *inherits* the `MainCamera` tag from the base prefab, so `SpawnClone` retags the fresh clone's camera `Untagged` and disables its duplicate `AudioListener` (the player keeps control on spawn: `CloneActive = false`). Skip this and both bodies behave as the active view.
- `SwitchClone()` hands control over by **retagging the active camera as `MainCamera`** (the other `Untagged`) and toggling `FPS_Controller` + `CharacterController` between the bodies. It deliberately **does not** toggle `GrabScript` — that stays enabled on the player as the sole grabber (see grabbing section).
- `DestroyClone()` hands control back, animates the split closed, then calls `ReleaseAsRagdoll()` — it does **not** `Destroy` the clone GameObject.
- `CloneActive` (public bool) tracks which body has control.
- **Split-screen culling masks:** each body's camera renders the *other* body plus its *own* first-person arms — never its own body or the other's arms — plus the shared `DeadClone` layer. Player cam = `PlayerArms(11)` + `CloneBody(13)` + `DeadClone(14)`; clone cam = `CloneArms(12)` + `Player(10)` + `DeadClone(14)`. The clone's mask is a prefab-variant override in `CloneNested.prefab` (`m_CullingMask.m_Bits`); when you add a layer that both views must see, update **both** masks.

### First-person arms: procedural IK + retargeted sway (`Character/GrabIK.cs`, `Character/ViewmodelArms.cs`)
There are no hand-authored arm/finger clips. Both systems live on the body root (so they propagate base → variant) and each drives its *own* `Camera/Arms/metarig`. That viewmodel skeleton is a separate **Rigify**-named rig (`upper_arm.R`, `forearm.R`, `hand.R`, `palm.01.R`, `f_index.01.R`, `thumb.01.R`, …) with different bone names **and** axes than the body's Humanoid rig, so they can't be name-matched or Humanoid-retargeted.
- **`GrabIK.cs`** (LateUpdate) — a two-bone IK solver bends the right arm to reach the held object, and each finger phalanx curls until it contacts the held collider (`Collider.ClosestPoint`) so the hand conforms. **Rig quirks that are load-bearing:** the IK "hand" tip resolves to **`palm.01.R`**, *not* the wrist `hand.R` — `palm.01.R` uniquely parents *both* the index and the thumb, while `hand.R` parents four metacarpals (`palm.01..04.R`). Fingers are collected from `hand.R` so all five are driven. `m_OrientHandToAnchor` applies `m_HandGripEuler` **relative to the rest pose** (zero = natural); it must not snap a bone to an absolute world rotation, because the rig's bones carry a large baked roll. Curl axes/angles are serialized (rig-dependent); `m_DebugOverrideWeight` scrubs the grip pose without playing.
- **`ViewmodelArms.cs`** (`[DefaultExecutionOrder(100)]`, so it runs *after* GrabIK) — (1) *retarget* copies the body's animated arm swing onto the viewmodel bones via a basis change captured at startup (LateUpdate), fading the right-arm swing out under `GrabIK.GripWeight` while gripping; (2) *sway* is procedural walk-bob / breathing / look-sway on the whole `Arms` container (Update).
- **Externally driven reach (`SetReachTarget`/`ClearReachTarget`, on both `GrabIK` and `BodyGrabIK`).** A world object can push a world point that *overrides* the held-object target, posing a body's hand onto itself — the clone-button caps and the `Lever` handle both do this. `GrabIK`'s overload takes an optional **grip collider**: pass one and the fingers curl around it using the same contact solve held objects get (a lever handle); leave it null for a flat-palm reach (a button face), because with no collider to stop them the fingers would curl to full angle and make a fist against the button. A pusher whose target *moves* must re-aim every frame, and must `ClearReachTarget()` when it lets go or the arm stays stuck out.
- **Gripping/sway is gated, not toggled.** Both bodies' components run every frame and each decides whether to act. Look-sway runs only for the active `MainCamera` body. `GrabIK` grips only for the body that is *holding* something: it finds the canonical grabber by tag `Main`, then grips iff `GrabScript.IsHolding(this body's camera)` — so the grip pose stays with the body that grabbed even after control switches away from it.

### Third-person grab pose (`Character/BodyGrabIK.cs`)
Cosmetic reach for the **visible humanoid body** (the `FirstCharacter` model that the *other* split-screen camera renders), distinct from `GrabIK`, which poses the first-person viewmodel arms only the holder's own camera sees. It must sit on the same GameObject as the Humanoid `Animator` (so `OnAnimatorIK` fires) and that controller layer needs **"IK Pass" enabled**. Using Unity's built-in Humanoid IK it eases the hand out toward the held object while this body is a holder — gated exactly like `GrabIK` (resolve the grabber by tag `Main`, reach iff `GrabScript.IsHolding(this body's camera)`) — so a carrying clone visibly extends its arm and the idle body keeps its normal pose. A dismissed corpse's Animator is disabled, so no reach is applied to ragdolls.

### Locomotion animation (`Character/CharacterAnimator.cs`)
On each body root; finds the child body `Animator` (the one with a controller assigned, not the controller-less arms Animator). Drives a single float **`Speed`** parameter from the body's *actual* horizontal movement (position delta), not from input. Because it measures real movement, the controlled body plays Walking while the idle body stays in Idle with no coupling to `Cloning`. The controller (`Models/AnimationsAndControllers/MainCharacterController.controller`) is just Idle ⇄ Walking with `Speed` threshold transitions.

### Ragdoll on clone dismissal (`Character/HumanoidRagdoll.cs`, `Character/Ragdoll.cs`)
`HumanoidRagdoll.Create(animator, velocity)` builds a ragdoll **at runtime** from the Humanoid avatar: it looks up the 11 standard bones via `Animator.GetBoneTransform`, adds Rigidbodies + Colliders + CharacterJoints (collider sizes computed in bone-local space so they're scale-correct), disables the Animator, and goes dynamic. `Cloning.ReleaseAsRagdoll()` calls it, then: retags the corpse off `Clone` (so a new clone can spawn), disables its controller/grab/camera components, adds a **`Ragdoll`** marker, **moves the corpse's model subtree to the `DeadClone` layer** (so every split-screen view renders corpses — live bodies on `CloneBody` are culled by the other view), and **destroys the corpse's `Camera` GameObject** once the split finishes (the first-person `Arms`/`CameraViewArms` are children of that camera and would otherwise hang in mid-air). The `Ragdoll` marker is how `GrabScript` recognises a corpse's body parts as grabbable. Ragdoll tuning (masses, joint limits, limb thickness) is constants in `HumanoidRagdoll.cs`.

### Object grabbing (`Character/GrabScript.cs`)
**Physics-based**, with a **single grabber**: the player's `GrabScript` (tag `Main`) — the target of all grab input — grabs on behalf of whichever body is active (raycasts from `Camera.main`). A hit is grabbable if its collider is on the `Pickable` layer **or** under a `Ragdoll` marker, and has a non-kinematic Rigidbody. At pickup it **captures the grabbing body's camera** (each `Hold`'s `HoldCam`) and each `FixedUpdate` drags that hold toward *that* camera's `HoldPoint` — so a held item **stays with the body that grabbed it across control switches** instead of following `Camera.main` to the newly-controlled body.
- **Rigid pickups** are pulled by velocity and rotated to the anchor (so they sit gripped, not tumbling).
- **The ragdoll** bone you aimed at is made **kinematic** and `MovePosition`/`MoveRotation`-ed to the hand each step (position + a rotation offset captured at grab), so it pins firmly and turns with the holder while the rest of the body dangles from it through the joints.

Holds live in a **`List<Hold>` keyed by the grabbing body's camera** (not a single global slot), so the player and the clone can each carry their own object simultaneously (one per body). Other systems query by body camera: `IsHolding(bodyCam)`, `GetGrabWorldPosition(bodyCam)`, `GetHeldCollider(bodyCam)` (used by `GrabIK`/`BodyGrabIK` to pose the holder's arms), and `IsHeldRigidbody(rb)` (used by `KeyCardScanner` to test whether a card is actually being carried). `Physics.IgnoreLayerCollision(heldLayer, Player)` stops a held object from shoving the carrier while held; it's restored on release. Move/rotate the `HoldPoint` anchor (or later parent it to a hand bone) to tune where/how things are held.

### Puzzle doors and conditions (`Door/`)
A small, decoupled, **event-driven** door framework (no per-frame polling):
- **`Door.cs`** — a reusable **procedural** actuator (no Animator clips). It tweens one or more serialized `DoorPart`s (a `Transform` plus a local position/rotation offset) between the **closed pose captured at `Awake`** and an open pose, using the same `SmoothStep` easing as `Cloning`'s split-screen animation. A sliding double door is two parts with opposite offsets; a hinged door is one part with a rotation offset. Authors place the door **closed** in the editor. `Open()`/`Close()`/`Toggle()` drive it; re-issuing the current state is a no-op (so a lock re-evaluating won't restart the tween).
- **`DoorCondition.cs`** — abstract base for anything that satisfies part of a door's requirement. Subclasses call the protected `SetMet(bool)`, which fires `OnChanged` **only on an actual transition**; a lock reads `IsMet` and subscribes to `OnChanged`. New condition types plug in without touching `Door`/`DoorLock`.
- **`DoorLock.cs`** — aggregates conditions (auto-collected from children if unset) and drives a `Door` (auto-resolved from parents if unset). `Mode` = `All`/`Any`/`AtLeast`, plus latch (stay open once opened), auto-close, and a close delay. Re-evaluates only on a condition's `OnChanged`.
- **Conditions** (`Door/Conditions/`): **`KeyCardScanner`** — met while an accepted card (tag `m_AcceptedTag`, default `KeyCard`) is BOTH inside its trigger AND being held (`GrabScript.IsHeldRigidbody`); its LED is recolored red/green via a per-renderer material instance (see gotcha). **`PressurePlate`** — met while a qualifying body (layer mask, default `Player`) stands on its trigger. **`InteractButton`** — a latching switch or momentary button pressed via `Interactor`, with an `OnPressed` UnityEvent for sound/VFX. **`CloneButtonLink`** and **`Lever`** — see the sections below.
- **The signature puzzle:** two `KeyCardScanner`s (or two `PressurePlate`s) under one `DoorLock` in `Mode.All` require both satisfied at once — one by the player, one by the clone. The other two conditions are the same idea in different clothes: `CloneButtonLink` makes the pairing explicit (two slots, one per body, at different panels), while a held `Lever` inverts it — one body is *spent* holding the lever so the other can be somewhere else.
- **`Character/Interactor.cs`** — player-owned interact actor (same single-actor-on-`Main` pattern as `GrabScript`): on the interact key it raycasts from `Camera.main` **ignoring triggers** and calls `Interact()` on the first **`IInteractable`** found on the hit collider *or its parents* (`GetComponentInParent`) — so the component goes on a model root and any solid child collider reaches it. The clone inherits the actor but its `InputManager` is disabled, so only the player's input fires it. Implementors identify the acting body as `Camera.main` at the moment of the press.
- **Runtime material-tint gotcha (load-bearing):** to recolor one object's material at runtime (the scanner LED) without affecting others sharing the asset, edit a **per-renderer material instance** (`renderer.materials[i]`) — *not* the shared `Material` (that mutates the `.mat` on disk for every user) and *not* a `MaterialPropertyBlock` (URP's SRP Batcher ignores per-renderer block overrides of `_BaseColor`/`_EmissionColor`, which live in the `UnityPerMaterial` CBUFFER). Textures are *not* in that buffer, so a property block **is** fine for per-screen texture swaps (e.g. camera-feed monitors).

### Paired clone buttons (`Door/Conditions/CloneButtonPanel.cs`, `CloneButtonLink.cs`)
The two-bodies-at-once puzzle in its most explicit form, split into **state** and **view**:
- **`CloneButtonLink`** is the `DoorCondition` and holds *all* the state: one pair of slots (`Left`, `Right`) that the two bodies claim between them. It sits on its own bare GameObject at the scene root (`CloneButtonLink`) and is wired into a door's `DoorLock` **by explicit reference** — not by parenting, so the lock's auto-collect-from-children never sees it. In `DemoLevel` it drives `SlidingDoors` (`Mode.All`, **latched**, auto-close off), so those doors stay open once solved.
- **`CloneButtonPanel`** is only a display plus the thing you look at. Every panel shows the *same* two slots, so pressing the left cap at one panel lights the left cap on **every** panel — which is how each body can see what its partner has already claimed from across the room. Panels self-wire: the three renderers are found by child name (`ButtonLeft`, `ButtonRight`, `Indicator`) and the link via `FindFirstObjectByType`. Two instances, deliberately far apart: `QuestObjects/CloneButtons` and `CloneButtons (1)`.
- **The rules that force two bodies:** the first press takes `Left`, the second `Right`; pressing again *releases* your own slot, so one body can never hold both; `m_RequireDifferentPanels` forces the two claims to be at *different* panels; and `m_ReleaseDistance` is deliberately both the maximum press range **and** the walk-away release range, so a press can never be made from a spot that would release it on the next frame. Both slots held at once = met.
- **A slot is keyed to the pressing body's camera transform** — the same identity token `GrabScript` and `Lever` use — so a claim survives control switching. A dismissed clone's camera is destroyed with it, which makes its slot read as free again.
- The cap a body holds down gets that body's hand through `GrabIK`/`BodyGrabIK` `SetReachTarget`, re-aimed every frame as the cap sinks, and with no grip collider so the palm stays flat. **Only the panel actually pressed at gets a hand**; the mirrored caps are display-only. The anchor is the cap **renderer's `bounds.center`**, not its transform: all four parts of the `CloneButtons` mesh pivot at the panel origin, which makes the transforms useless as anchors.

### Held levers (`Door/Conditions/Lever.cs`)
A `DoorCondition` + `IInteractable` that goes on the lever's **root** (whose children are the handle and the base). Interacting swings the handle by a serialized local-euler offset — default **180° about the handle's own X axis** — with the same `SmoothStep` easing as `Door`.
- **Hold-to-keep is the whole point.** By default the lever stays thrown only while the body that pulled it stays within `m_ReleaseDistance` of the grip, so using the lever *spends a body*: the lever and whatever it drives can only be combined by the player and the clone together. `m_Latching` turns it into a plain stay-put switch instead (the hand then only rides the swing).
- **The holder is a specific body, not "whoever is in control."** Identity is the pulling body's **camera transform** — the same token `GrabScript.IsHolding` and `CloneButtonLink` key on, valid because exactly one camera is tagged `MainCamera`. This is load-bearing: it is what lets the clone keep the lever thrown *after control switches back to the player*, without which a one-lever puzzle is unsolvable. It releases on a second interact, on walking out of range, or when the holder's camera goes null — `DestroyClone` destroys it, which is why dismissing the holding clone drops the lever.
- **Rotate by `AngleAxis` from the rest pose; never `Slerp` to the thrown pose.** At exactly 180° the shortest arc between two rotations has no defined axis, so a Slerp is free to swing the handle sideways off its hinge. The authored euler is split into axis + angle once at `Awake`, which also captures the rest pose — author the lever **resting**, as with `Door`.
- **The grip point should be a child of the handle** so it travels with the swing; the lever re-aims both IK systems at it *every frame*, which is what makes the hand follow the throw. The fallback is the handle renderer's `bounds.center`, because the handle's own transform sits at the hinge and barely moves. The handle's collider is handed to `GrabIK` as the grip collider, so it must be **convex** for the fingers to conform to it.
- Scene instance: `LeverSwitch` (root, holds `Lever`) → `Lever` (the handle: convex MeshCollider, child `GripPoint`) + `LeverBase`. It drives the lift below, not a door.

### Lifts and moving platforms (`MovingPlatform.cs`)
A lift is just a `Door` that travels upward — no new actuator. `Door` + `DoorLock` on `QuestObjects/LiftPlatform` tween the `Platform` child by a local position offset, with the `Lever` as the lock's only condition (no latch, auto-close, so letting the lever go lowers it). **Local offsets are in the parent's scaled space:** `LiftPlatform` is scaled `(3,2,2)`, so a local `Y 1.5` is a 3-unit world rise.
- **`MovingPlatform` carries the riders, and that is load-bearing rather than polish.** Neither body rides a mover on its own: the controlled body's `CharacterController` is not pushed by moving colliders, and the **idle body's controller is disabled outright** by `SwitchClone`, leaving it with no collider for physics to act on. The idle body is precisely who rides — the puzzle puts one body at the lever and the *other* on the platform — so the lift has to move it explicitly.
- It measures its **own transform delta** in `LateUpdate` (after `Door`'s tween coroutine has already moved it that frame, and at `[DefaultExecutionOrder(-10)]` so a rider finishes moving before `GrabIK`/`ViewmodelArms` pose its arms) and applies that delta to any body whose **feet** sit on the top face: `CharacterController.Move` when the controller is enabled, direct transform placement when it isn't. Testing the feet rather than overlapping the whole capsule is what stops a body on the floor *beside* a lift from being dragged with it. Bodies are resolved by tag (`Main`/`Clone`) and re-resolved whenever a cached one no longer carries that tag — which is how a dismissed corpse drops out. Loose `Pickable` props are **not** carried; PhysX depenetration shoves them along.
- **Anything moved at runtime must not be marked Static.** A **Batching Static** renderer cannot be moved — its vertices are baked into a combined mesh in world space, so the mesh would sit still while the collider and its riders rise. `Platform`'s static flags were cleared for this, which also drops it out of the baked lightmap: it now lights from realtime lights/probes, and the scene wants a re-bake.

### Modular corridor kit and snapping (`Modular/CorridorPiece.cs`, `Editor/Modular/`)
The octagonal corridor pieces in `Prefabs/EnviromentModel prefabs/EnvironmentCorridors/` (`Corner`, `CorridorType1`, `CorridorType2`, `Cross`, `TCross`) are assembled with **`Tools > Qlone > Corridor Snap`**, which joins them **opening-to-opening** rather than by transform or grid. That indirection is the whole point:
- **The pivots are useless as anchors.** All five come out of one `Demo_Map.blend` with a baked `-90` X rotation and `0.5` scale, and their pivots bear no relation to their geometry: `TCross`'s sits ~12.3 units from its own mesh, `Corner`'s is offset ~1.4 on two axes. **Bounding boxes mislead too** — a corner extends 4.0 toward each *open* side but only ~1.22 past the junction on its *closed* sides, so centring two AABBs on the shared axis is off by ~1.39.
- **There is no single grid size.** `Cross` is a true 8.0 tile (arms at ±4.0) and `TCross` matches it on its through-run, but the straights are **7.23** and **7.35** long. A fixed-grid snap would be wrong for two of the five pieces.
- **`CorridorPiece`** (in `Scripts/Modular/`, so it can live on prefabs) therefore stores each open end as a **socket**: local-space centre + outward direction + radius. Sockets are baked onto the **prefab assets**, so scene instances inherit them. All openings are ~1.13 world radius, which is the "same dimension" the pieces share.
- **Sockets are found automatically from the mesh, not authored.** `CorridorSocketBaker` walks **boundary edges** (edges used by exactly one triangle): an open-ended tube's openings are boundary loops, while a closed side is capped and has none. Two things make that work on this export — vertices are **welded by position first** (5 material submeshes plus split normals duplicate verts, and every duplicate would read as a false boundary), and **coplanar concentric rims are merged** (a wall-thickness opening yields an inner and an outer loop). It recovers 2/2/2/4/3 openings across the kit with no per-piece setup.
- **Snapping applies the EXACT yaw the join needs, then tidies.** Rotation is yaw-about-world-up only, which preserves the baked `-90` X. Rounding the yaw *delta* to 90° up front is the tempting bug: a piece that arrived at an odd angle then lands in a correctly *positioned* but visibly **tilted** joint. So `CorridorSnap.AlignTo` rotates exactly, optionally rounds the result to 90° **only when already within `TidyRotationTolerance` (0.1°)** — enough to erase the kit's ~0.02° import drift (rotations read `270.0198`) — and **translates last**, so the openings coincide regardless. Verified across all 169 piece/socket combinations from a deliberately off-axis start: worst gap 3e-6 units, zero angular error, zero tilt.
- **Using it:** *Bake* once per kit; then pick a piece in the palette and **click any green opening in the scene view** to place it already butted on. `Alt+J` snaps a dragged selection to the nearest opening, `Alt+K` cycles *which* of its sockets connects (this is how you flip a corner's turn). *Find gaps* lists every pair of openings that face each other but do not meet, with a one-click fix. Scene-view colours: **green** free, **blue** joined, **yellow/red** joined with a gap.
- **Gotcha:** the corridor instances in `DemoLevel` are marked **Static**. That is fine for editor-time assembly, but moving them invalidates the baked lightmap — the scene wants a re-bake after a rebuild (same caveat as `Platform` under *Lifts and moving platforms*).

### Security-camera feeds (`SecurityMonitor.cs`)
A camera-to-screen surveillance chain, entirely Editor-wired: `=======SecurityCameras=========/StartRoom/Camera1..3` each render into their own `Assets/_App/SecurityCameras/StartRoom/CameraN.renderTexture`, and each `Monitor` object's `SecurityMonitor` shows one of them — `Monitor (6)` → Camera1, `Monitor (8)` → Camera2, `Monitor (7)` → Camera3. To add a feed: new Camera + new RenderTexture asset, set the RT as that camera's **Target Texture**, then assign the same asset on the monitor.
- **Why a `MaterialPropertyBlock` is right here but wrong for the scanner LED:** every monitor shares one `Screen.mat` (slot **2** of the Monitor mesh — `StandColor`, `MonitorFrame`, `Screen`), so assigning an RT to the material would light every screen in the level with the same feed. Textures live **outside** the `UnityPerMaterial` CBUFFER, so a per-renderer property-block override survives URP's SRP Batcher — the exact opposite of the `_BaseColor`/`_EmissionColor` case, which needs a real material instance. Use the **`materialIndex` overloads** of `Get`/`SetPropertyBlock` so the override is scoped to the screen slot and leaves the stand and frame untouched.
- The feed cameras' **culling mask excludes both arm layers** (`PlayerArms(11)`/`CloneArms(12)`) while including `Player(10)`, `CloneBody(13)`, `DeadClone(14)` and `Pickable(9)`, so a monitor shows the bodies and corpses but never a floating pair of viewmodel arms. That makes these a **third** set of masks to update when you add a layer every view must see (the two body cameras are the others).
- **Gotcha:** all three feed cameras currently carry an `AudioListener`, which is why Play mode logs *"There are 4 audio listeners in the scene"* (`Cloning` goes out of its way to disable the clone's duplicate). Strip the listener off any new feed camera.

### Tags and layers are a hard contract
Code hardcodes layer **numbers** and looks objects up by **tag string** at runtime. Reordering `ProjectSettings/TagManager.asset` will silently break things.
- Layers (by index): `8 PostProccesing`, `9 Pickable`, `10 Player`, `11 PlayerArms`, `12 CloneArms`, `13 CloneBody`, `14 DeadClone`. `GrabScript` treats `Pickable` as grabbable and ignores collisions between the held object's layer and `Player`. Live clone body/arms sit on `CloneBody`/`CloneArms`; a **dismissed corpse is moved to `DeadClone`** so both cameras render it (resolved at runtime via `LayerMask.NameToLayer("DeadClone")`). A newly-added layer must be saved to disk (*File → Save Project*) and given a sensible Physics collision-matrix row, or it collides with everything by default.
- Tags used in code: `Main` (player root; also how `GrabIK`/`ViewmodelArms` find the canonical grabber `GrabScript`), `Clone` (live clone, found via `FindGameObjectWithTag`; a corpse is retagged `Untagged` so it's no longer found), plus the built-in `MainCamera`/`Untagged` swapped during control switching. `MovingPlatform` resolves *both* bodies by those two tags to find its riders, and relies on the corpse retag to stop carrying a dismissed clone. Other defined tags: `KeyCard`, `PickUp`, `CloneArms`.

### Narrative text (`TextController.cs` + `Editor/TextControllerEditor.cs`)
A coroutine typewriter effect that prints `m_Text` one character at a time into a uGUI `Text`. Control characters: `/` clears the textbox; a `/` *following* a character inserts a pause (`TextPause`). The custom inspector adds a **"Get Text File"** button that loads a `.txt` (e.g. `Assets/_App/NarrativeText/NarrativeText.txt`) into `m_Text` via a file dialog.
